QUESTION 2: VECTORIZER LOADING
How is the vectorizer loaded in app.py? Is it stored in a file or initialized dynamically?
================================================================================
FINDING: INITIALIZED DYNAMICALLY (HARDCODED GLOBAL VARIABLE)

Detailed Inspection:
- In `app.py` (lines 99-107), the vectorizer is NOT loaded from a serialized file
  (e.g., vectorizer.joblib).
- Instead, it is instantiated statically as a global module-level object:
  ```python

  vectorizer = HashingVectorizer(
      n_features=NUM_FEATURES,
      alternate_sign=False,
      norm="l2",
      lowercase=True,
      token_pattern=r"(?u)\b\w\w+\b"
  )
  ```
- Rationale: `HashingVectorizer` is stateless; it uses the MurmurHash3 algorithm to
  map tokens directly to fixed feature indices without needing a learned vocabulary.
  Because it stores no state, it can be initialized dynamically without loading from disk.
- Critical Impact: Because `NUM_FEATURES = 512` is hardcoded at line 99 of `app.py`,
  any incoming text passed to `vectorizer.transform([message])` produces a matrix
  with exactly 512 columns, irrespective of what model file is loaded on disk.

QUESTION 8: ESP32 MEMORY FOOTPRINT
Can ESP32 handle 2048 float weights (8KB) in flash and RAM?
================================================================================
FINDING: YES, FULLY CAPABLE. BUT WITH ONE CRITICAL STACK CONSIDERATION.

Detailed Hardware Analysis:
1. Hardware Specifications (ESP32 / ESP-WROOM-32):
   - Flash Memory (ROM) : 4 MB (4,096 KB) standard (up to 16 MB)
   - Internal SRAM (RAM): 520 KB total (~320 KB usable for Arduino heap and stack)
   - Clock Frequency    : Dual-core Xtensa LX6 at 240 MHz

2. Flash Storage Analysis (Program Memory):
   - `MODEL_WEIGHTS` is declared `static const float MODEL_WEIGHTS[NUM_FEATURES]`.
   - In GCC for Xtensa, `static const` global arrays are stored in RODATA in Flash ROM.
   - Array Size: $2048 \times 4\text{ bytes} = 8,192\text{ bytes} = 8.0\text{ KB}$.
   - Flash Usage: $8\text{ KB} / 4,096\text{ KB} \approx 0.19\%$ of flash space.
   - Impact: Completely negligible.

3. RAM Analysis (Runtime Memory):
   - Weights in Flash do NOT consume SRAM.
   - However, during inference, `createFeatures()` computes the feature vector:
     `float features[NUM_FEATURES];`
   - Feature Vector Size: $2048 \times 4\text{ bytes} = 8,192\text{ bytes} = 8.0\text{ KB}$.
   - Overall Usable SRAM: ~320 KB. 8 KB represents only $2.5\%$ of available RAM.

4. CRITICAL ARCHITECTURAL WARNING (ESP32 LOOP STACK OVERFLOW):
   - In `EdgeSpam_Demo.ino` line 274:
     ```cpp
     void loop() {
         ...
         float features[NUM_FEATURES]; // ALLOCATED ON THE LOCAL TASK STACK!
     ```
   - In the ESP32 Arduino Core, the default FreeRTOS stack size assigned to `loopTask`
     is exactly 8,192 bytes (8 KB) (`CONFIG_ARDUINO_LOOP_STACK_SIZE=8192`).
   - If an 8 KB array is allocated on an 8 KB stack alongside function call frames
     (display routines, MurmurHash, Wire I2C), A RUNTIME STACK OVERFLOW IS IMMINENT!
   - Result: ESP32 panic (`Guru Meditation Error: Core 1 panic'ed (Unhandled debug exception / Stack protection fault)`).
   - Solution: Change line 274 to:
     ```cpp
     static float features[NUM_FEATURES];
     ```
     or declare `features[NUM_FEATURES]` as a global variable outside `loop()`.
     This moves the 8 KB buffer to the BSS section in DRAM, where over 250 KB is free,
     completely eliminating the stack overflow risk!
